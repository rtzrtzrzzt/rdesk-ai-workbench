# 一键启动与关闭

Linux/macOS 入口是 `start.sh`、`stop.sh`，Windows PowerShell 入口是 `start.ps1`、`stop.ps1`。无参数执行启动脚本即可；`start.sh stop` 与独立关闭文件使用同一逻辑。Ubuntu 图形环境没有终端时，脚本会在可用的 GNOME Terminal 中显示进度，完成后按 Enter 关闭窗口；文件管理器需选择“以程序运行”。通过终端执行则直接显示在当前终端。

启动完成后的服务独立运行，关闭进度窗口不等于停止后台服务。启动过程中 Ctrl+C 取消本次操作并清理本次新启动的组件，已复用的服务保留；独立关闭入口则停止所选配置的全部受管组件。已有资源无法确认时保留状态，显示具体失败阶段与私有日志位置，不以“已发停止信号”或端口消失代替模型资源回收凭证。

## 当前启动顺序

1. 检查所选配置、平台及既有模型运行归属。
2. 只恢复已有、可核验的项目 PostgreSQL，并实际检查应用数据库连接；未配置或外部连接不可用时停止，不创建替代数据库。
3. 复用或启动已准备的 SearXNG，核对受管身份及非生成服务响应；不把响应就绪当作搜索结果验收。
4. 复用受同一 boot 的有效 guard 监管、实际参数匹配的模型；否则复用既有 PLE 清理规则保留一代缓存，再建立 fresh-PLE 并独立启动原 modelctl guard。固定权重、128K、MTP 和内存保护保持原配置。
5. 模型真实 `/ready` 成功后启动 API、agent/file/media Worker、凭据服务，通过原 CLI 的五个组件身份、API监听和三类Worker心跳检查，再打开页面。媒体Worker不预先加载FLUX；实际生成再按阶段准入，见[本机生成环境](../media/README.md)。

模型日志可能有主权重、MTP 权重两轮分片，11/11 后仍可能初始化计算图。进度使用本轮 guard 对应的实际日志，阶段编号不是整体百分比，不依据时间推算完成率。单次本地模型等待默认40分钟，可配置；不会为赶超时自动换模型或连续重试加载。

关闭顺序为工作台及受管执行、模型、搜索、数据库。外部服务由其原管理器维护，启动器不接管或结束外部进程。日常启动不启动8771/8772/8773验收副本及其独立数据库。

应用停止的最后一步需要读取数据库，确认后台长任务的资源已经关闭。受管数据库已停时，关闭入口会短暂恢复同一已有集群完成核对，随后再次关闭；不会重新启动模型或工作台，也不创建数据库。外部数据库不可用时保留未确认状态，不能绕过任务资源核对宣称成功。

系统重启后，普通模型关闭会先复用模型控制器已有的跨boot核对：仅实际boot变化可证明旧资源已消失时，锁内归档原记录再写关闭凭证；同boot或证据不足继续保留记录。取消本次启动仍只处理本次创建的资源。CLI关闭入口加载完整数据库表定义，避免尚有命令记录时因缺少users表声明而中断。命令跨boot与旧记录的明确确认边界见[命令模块](../../apps/server/src/workbench/modules/processes/README.md)。

## 本机私有配置

默认读取 `.local/launcher/profile.json`；示例见同目录下的 `launcher-profile.example.json`。文件须满足原私有配置权限检查，不进入 Git、源码包或公开静态资源。`--profile /绝对路径/profile.json` 可明确选择另一份配置。内容是 JSON，不作为 shell/PowerShell 代码执行。

- `environment`：保存已选的 `WORKBENCH_DATA_DIR`、端口、前端目录及数据库连接等应用配置。当前进程显式环境逐项优先，包括显式空值。
- 命令并发可用`WORKBENCH_COMMAND_MAX_ACTIVE_PER_RUN`及`WORKBENCH_COMMAND_MAX_ACTIVE_TOTAL`配置，默认2/4，均1..32且前者不大于后者。以字符串整数存入`environment`，重启应用后生效；不改变主模型或推理并发。禁止为查看这两项而输出含口令的完整profile。
- 未显式选择 profile，但当前环境指定了数据目录或数据库连接时，默认本机 profile 不会混入另一实例。
- `database`：`auto` 从应用数据根的受管配置判断；显式连接按外部数据库处理。`managed` 恢复该数据根的受管集群；`legacy` 仅显式用于此源码目录已准备的开发集群；`external` 只核对应用 SQL 连接。
- `search`、`model`：`managed` 使用现有本机控制器，`external` 使用页面配置的已有连接，`disabled` 不托管该项；`auto` 根据已有本机配方选择。外部模型和搜索的能力需在工作台单独核对，不由启动完成推定。
- `model_timeout_seconds`：60～86400秒，默认2400秒。

`--check`、`doctor`、`--prepare-database` 和生命周期命令使用同一已选 profile。显式数据库连接存在时，原数据库准备命令仍拒绝创建另一集群。`--install`、`--rebuild-web` 和首次准备依然是显式动作，普通启动不自动安装。需要单独控制应用时使用 `--app-only`。

控制状态、分阶段记录和诊断日志位于 `.local/launcher/`。记录包含真实状态、耗时和安全日志位置，正常进度不打印连接口令、API key 或模型完整调试参数。

## 平台边界

两个入口共用 `scripts/bootstrap.py` 和 `scripts/services/stack.py`。现有 Spark 模型监管器依赖 Linux pidfd/subreaper，搜索与私有数据库开发配方也依赖 Linux；Windows/macOS 使用这些受管模式会提前说明条件缺失，不能仅通过替换脚本后缀获得兼容。对应平台配置并自行准备原生外部服务后，应用仍可走其现有原生入口。

本轮在 Ubuntu24.04 ARM64 / DGX Spark 实际通过完整启停、启动中Ctrl+C清理、真实主页面本地模型消息、图形进度窗口、复用及重复关闭。全部关闭状态启动约10分37秒，复用约1秒；这是本机此次观察，不是固定时延承诺。Windows PowerShell、macOS、真正离线首次安装及其他引擎的本机受管启动继续等待相应环境验证。
