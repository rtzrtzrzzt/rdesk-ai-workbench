## 1. 交付目标与边界

### 1.1 用户获得什么

首个使用场景是单人、多工作区，可通过局域网访问的本地 Web 工作台。主要计算主机是 NVIDIA DGX Spark，三平台原生运行均纳入设计：Linux、Windows、macOS。Spark 是优先进行真实验证的平台，其他平台按组件逐项验收，不能将“Python 能运行”写成“整套产品已支持”。

用户正常启动时不需要进入源码目录、不需要手动激活 Python 虚拟环境，也不需要运行 npm、Vite 开发服务器或多个终端。发行版提供受控启动器，负责找到自身运行环境、检查配置、启动后台组件、显示故障和打开浏览器。源码开发运行与用户发行版是两条明确的路径。

“本地应用”不等于只有一个进程，也不要求把所有工具常驻。需要持久保存的是运行状态、用户数据和恢复依据；解析器、OCR、ASR、浏览器和沙箱按任务需要启用。模型服务可长期驻留，以避免每次对话重新加载大模型。

### 1.2 固定架构约束

| 项目 | 本版设计 | 原因与边界 |
| --- | --- | --- |
| 前端 | React、TypeScript、Vite 构建静态资源 | Vite 属于构建工具；发行版提供构建产物 |
| 应用后端 | FastAPI，API 与 RunWorker 独立进程 | 长任务不依附请求连接或页面生命周期 |
| Agent 运行时 | LangGraph 为唯一运行时 | 不再引入第二套 Agent 生命周期和恢复系统 |
| 事实数据库 | 普通 PostgreSQL | 保存会话、任务、事件、审批、能力配置、索引和运行恢复元数据 |
| 记忆 | Markdown 文件，受工作区和用户作用域约束 | 不安装向量数据库；全文检索及索引可重建 |
| 作业协调 | 初版 PostgreSQL 任务表、租约、持久事件与通知 | 不要求同时安装 Celery、Redis 和另一套作业系统 |
| Valkey | 可选的通知、缓存或协调加速 | 不承载唯一事实；删除后应能从 PostgreSQL 恢复 |
| 子 Agent | 最多 3 个，深度 1 | 是组织任务的限制，与模型同时推理的数量分开 |
| 模型推理并发 | 初始为 1，由能力和资源实测后调整 | 允许有多个待调度 Agent，不代表同时加载或执行多个大模型 |
| 部署 | 原生优先 | Docker 仅作为可选的单项隔离工具，不成为整套工作台的必要基础 |
| 演进 | 预留用户身份与工作区授权边界 | 首版不因预留多人而引入组织计费、企业 SSO、Kubernetes 或集群调度 |

Vite 官方将生产构建和本地预览分开，明确预览服务不是生产服务器；本设计因此采用静态产物交付，不把 `vite preview` 或开发服务器藏在启动器后面。[Vite 部署说明](https://vite.dev/guide/static-deploy.html)

## 2. 发行版结构与进程边界

### 2.1 运行拓扑

```text
用户浏览器（本机或经显式开启的 LAN）
          |
          | 同源 HTTPS/LAN；本机仅回环访问
          v
受控入口：静态前端 + FastAPI API + 事件连接
          |
          +---------- PostgreSQL ----------+
          |  会话/任务/事件/租约/审批/索引  |
          v                                |
RunWorker：唯一 LangGraph 运行控制 ---------+
          |
          +-- ModelGateway --> 长驻模型服务 / 授权外部 API
          +-- ToolExecutor --> 按需文件/OCR/ASR/浏览器进程
          +-- MemoryService --> Markdown + 可重建检索索引
          +-- ArtifactStore --> 不可变产物版本 + 受限下载
          +-- DesktopProvider --> 已配对的目标主机 Companion

Launcher / OS Supervisor
  管理进程、退出、日志、服务状态；不代替数据库中的任务状态
```

静态前端可由应用入口直接提供；LAN HTTPS 可以由已存在且受支持的反向代理承担。反向代理不是本机回环模式的默认强制依赖。默认生产发行路径不需要 Node.js 常驻；如果选用另需 Node 服务的可选 UI Runtime，须单独列入组件清单与进程监督，不能沿用默认路径的依赖说明。API 不加载模型权重，不运行 CPU 密集解析，不把工具执行放入进程内的短命后台任务。

FastAPI 部署文档把进程启动、重启、复制和内存作为独立部署问题。将 API 与计算进程拆开，是本项目的职责选择，不以增加 HTTP worker 数量代替长任务队列。[FastAPI 部署概念](https://fastapi.tiangolo.com/deployment/concepts/)

### 2.2 进程与生命周期

| 组件 | 生命周期 | 启动条件 | 故障后的处理 |
| --- | --- | --- | --- |
| Launcher | 用户启动后运行，或委托给系统监督器 | 用户点击启动 | 可重新打开并重新连接已有实例，不能重复拉起整套进程 |
| PostgreSQL | 独立本地服务或已授权的现有实例 | 首次安装配置后 | 数据库不可用时停止接收新执行；不得退回内存事实源 |
| API | 常驻，初版单应用实例 | 配置与 schema 兼容 | 重启后从数据库提供当前任务和事件；不重提任务 |
| RunWorker | 独立常驻 | API 独立即可启动，但必须连接数据库 | 根据租约、checkpoint 和工具结果对账；禁止把所有处理中任务直接重跑 |
| 模型服务 | 按配置常驻或显式卸载 | 后端、模型、资源检查合格且用户已启用 | 标记部署不可用；保留队列，可切换到已授权且兼容的模型 |
| 文件处理器 | 每任务或受控小型进程池 | 任务需要且对应组件可用 | 保留部分产物与失败阶段，关闭进程树，按工具策略决定可否恢复 |
| 浏览器 | 每会话/任务，受 profile 与授权约束 | 用户启用浏览器能力 | 回收本应用拥有的上下文，不能结束用户无关浏览器 |
| Desktop Companion | 目标用户登录会话中运行 | 用户本机启用、配对并授予 OS 权限 | 桌面动作暂停；不能以重连为由自动补发未对账的点击 |
| Valkey（可选） | 启用后常驻 | 明确配置了可选加速功能 | 退化到数据库轮询/重建缓存；不丢已提交任务和审批 |

不把每个 Agent 映射为一个独立模型服务。根 Agent、子 Agent 和后台总结通过同一资源准入机制调用模型。Worker 重启不等于模型服务也必须重启；模型服务退出也不应导致数据库或前端退出。

### 2.3 启停与就绪语义

启动器执行顺序如下：

1. 取得本应用实例锁，确定安装版本、数据目录和用户配置；遇到已运行实例时只连接已有入口。
2. 检查配置格式、目录权限、所需端口和数据库连接；端口冲突显示占用和可选端口，不结束其他程序。
3. 检查数据库 schema 兼容性。迁移只能由一个受控迁移执行者操作，不能由 API 和多个 Worker 在启动时竞相迁移。
4. 启动 API、RunWorker，等待各自就绪；模型可以稍后独立加载。前端在“模型未就绪”时仍能打开设置、历史、诊断和已有产物。
5. 根据启用的模型部署执行加载前检查；仅在明确的加载预算内启动引擎，达到服务就绪和能力验收要求后才允许接收相应请求。
6. 显示各组件状态和地址；打开浏览器。不能用固定等待若干秒假定数据库或模型已启动成功。

至少区分进程存活、依赖可用、API 就绪、Worker 可接单、模型已加载、模型能力已验证。健康探测接口不得返回 API key、数据库 DSN、用户文件路径或历史内容。UI 的“运行中”以业务状态为准，不能由健康探测成功推导出来。

正常停止先停止接单，再通知活动任务进入可恢复停点，等待工具退出并释放租约，最后停止本应用拥有的进程。达到配置的退出期限仍不能安全结束时，保存已知状态，将结果不明的外部操作标为待对账。不得先强杀全部进程再把任务写成成功取消。未启用“同时停止模型服务”时，可以保留独立模型服务；界面须说明仍占用资源的组件。

监督器负责进程退出后的有限退避重启、日志路径与退出原因。应用负责任务恢复、幂等与权限。重启循环达到配置阈值后进入降级状态并显示诊断，不无限重启占满 CPU、磁盘或模型内存。

## 3. 安装体验与本地目录

### 3.1 开发运行和日常运行

| 路径 | 适用对象 | 必须提供的东西 | 不得误表述为 |
| --- | --- | --- | --- |
| 源码开发 | 实现者 | 版本锁、构建说明、开发启动脚本、必要检查 | 普通用户每次运行步骤 |
| 原生发行版 | 最终用户 | 前端构建产物、受控后端运行环境、启动器、清单、许可证、升级入口 | 仅下载源码后让用户自行装齐环境 |
| 可选工具组件包 | 需要 OCR/音视频/桌面等功能的用户 | 兼容平台说明、准确下载与空间信息、启停和卸载能力 | 默认所有功能均已装好 |
| 可选单项容器沙箱 | 需要额外隔离的已授权工具任务 | 镜像来源、资源和挂载边界、镜像清理入口 | 所有用户必须安装 Docker |

发行版按操作系统和 CPU 架构分别构建。后端运行环境独立于用户系统 Python，依赖来自锁定清单，不在每次启动时执行隐式更新。前端构建时使用锁文件，用户运行时只读取静态资源。内置运行环境的分发方式、签名和各平台打包工具在发布实现时锁定；不能把某一平台成功打包视为所有平台均能使用同一二进制。

第一版可以由受控安装器准备应用私有运行环境，但最终产品入口必须是启动器；不能永久要求普通用户记住虚拟环境路径和命令。安装器若需要联网获取运行时，必须在安装清单中明确显示来源、版本、预计下载量、安装位置和失败处理。

### 3.2 首次设置向导

向导按“检测—解释—选择—执行—报告”推进，用户可以在无模型时完成应用基础设置。

当前数据库前置准备采用原生终端入口：`--prepare-database doctor` 显式准备支持平台的项目私有 PG，或 `configure-database` 在 TTY 中验证并保存已有回环数据库连接。启动器能恢复已登记且身份完整的私有 PG；不会对不明目录重新 initdb。数据库就绪、迁移和检查点准备完成后，浏览器负责首次所有者创建和日常配置。当前没有无数据库 Web bootstrap 或 `/api/v1/setup/*` 安装 API；这些不能作为现有使用步骤。账户恢复另走停服后的本机 TTY。

1. 选择数据根目录与默认工作区目录，显示实际文件系统可用空间和写权限。工作区可以指向用户已有目录；不能为了安装而移动用户项目。
2. 检测 PostgreSQL：支持连接已授权的现有实例，或引导安装受支持的原生本地服务。复用实例时使用应用专属数据库和最小权限账户，不能把现有数据库升级、重配或清空。
3. 应用自身可用环境与模型环境分开检查。找到已有模型资产时支持手动选择目录、导入本地 manifest 和离线配置，默认不再次下载、复制或转换巨型权重。
4. 列出本次启用功能的组件清单。用户可先只启用文本和基础文件处理，再安装 OCR、ASR、Office 转换、浏览器、桌面驱动；高级功能仍保留在产品设计中，是否可用由安装与平台状态决定。
5. 展示将下载的每个包、权重或浏览器的来源、版本/提交、许可证、大小、解压/编译临时空间、目标目录及删除方式。下载与安装在用户确认的清单范围内执行。
6. 执行基础自检并报告结果。成功的是“应用基础已安装”还是“模型输入链路已验收”必须分开显示；可选组件失败不得把整个应用无条件判成不可运行。
7. 默认启用仅本机访问；LAN 是独立步骤，满足登录、会话和 HTTPS 条件后才开放网络监听。

新增下载使用默认源，例如 npm 默认 registry、PyPI 默认源、组件官方分发源。不得悄悄切换镜像或通过非官方脚本解决安装失败。下载任务支持进度、暂停/取消、续传条件和空间检查；中断文件保存在专门临时区域，不登记为可用组件。离线模式只能使用已有可验证资产，不伪造安装成功。

PostgreSQL 是必须明确处理的一次性系统依赖。本设计不假定三平台都有可以无管理员权限嵌入的完整 PostgreSQL 发行包；发布时必须逐平台选择官方或受支持的原生安装路径，说明服务账户、数据目录和卸载行为。应用可提供向导与诊断，但不能把“请自己装数据库”作为唯一安装体验，也不能未经授权变更系统服务。

### 3.3 目录职责

```text
应用安装根（可替换、尽量只读）
  releases/<应用版本>/
    launcher/
    backend-runtime/
    backend/
    web-static/
    manifests/
    licenses/
  current -> 当前发行版（Windows 采用等价受控版本指针）

应用数据根（跨升级保留）
  config/                 非秘密配置与版本
  state/                  实例锁、组件状态、临时通信信息
  users/<user_id>/
    AGENTS.md             工作台用户级全局规则
    memory/               用户级索引与主题记忆
  workspaces/<workspace_id>/
    memory/               Markdown 记忆，或指向授权工作区内的约定位置
    runs/<run_id>/STATE.md 当前任务的可读摘要，不替代数据库 checkpoint
    artifacts/            版本化产物与来源清单
    staging/              尝试中的部分产物，不作为已发布产物
  logs/                   脱敏、轮转、分组件日志
  diagnostics/            用户确认导出的诊断包
  cache/                  可重建、可清理，不能保存唯一业务事实
  components/             可选运行环境/解析器/浏览器/模型资产引用
  backups/                用户指定位置或备份任务清单

独立受管资源
  PostgreSQL data         由数据库服务管理，不当普通文件复制
  models/...              可复用现有位置，不强制复制到应用数据根
  用户工作区目录           原文件、项目、用户选择的输出位置
  OS Keyring              密钥；不可用时采用明确受限的替代存储
```

默认应用数据根为 Linux `$XDG_DATA_HOME/ai-workbench`（未设置时按 XDG 默认规则解析）、macOS `~/Library/Application Support/AIWorkbench`、Windows `%LOCALAPPDATA%/AIWorkbench`。配置、日志和缓存仍按各平台相应目录语义分开；用户可以显式选择其他数据根。绝对路径由 Launcher 统一调用平台路径适配层解析，可复用 `platformdirs`，不能把 `/tmp`、`~/.config` 或 POSIX 权限模型硬编码为三平台接口。可迁移数据与可重建缓存分开，减少备份量并避免清缓存丢会话。

数据库中的 artifact 使用逻辑 ID 与相对存储定位，不把某台机器的完整绝对路径当成可移植标识。工作区授权根保留映射，迁移后需要用户重新确认新路径。Windows 大小写、路径长度、盘符与锁文件语义，macOS 文件名规范化，以及符号链接、硬链接和网络挂载都必须在文件能力适配器中处理。

### 3.4 卸载和清理

默认卸载仅删除程序和本应用专属可重建缓存，保留数据库、工作区、记忆、产物、备份和已下载模型。彻底删除数据作为独立动作，列出真实路径和占用，要求用户明确选择。复用的数据库服务、共享模型目录、Docker、浏览器与其他应用组件不得随工作台卸载。

缓存清理采用可重建分类，不按“文件较老”粗暴删除。运行中 artifact、备份引用和模型 PLE backing 文件均可能在使用，必须先完成引用与活动租约检查。删除模型资产需显示哪些部署引用它，并先停用相关部署；不能以清缓存名义删除用户已有模型。

## 4. 三平台原生运行与能力探测

### 4.1 平台矩阵

下表区分平台设计与当前实测。“待验证”是明确状态；Spark 的已完成流程不能自动推广到其他操作系统。

| 维度 | Linux，优先 DGX Spark ARM64 | Windows 原生 | macOS 原生 |
| --- | --- | --- | --- |
| 应用入口 | 受控 Launcher；可集成 systemd 用户服务 | Launcher；按需用户登录任务或 Windows 服务 | Launcher；按需 LaunchAgent 或 LaunchDaemon |
| API/Worker | 原生 Python 运行环境、独立进程 | 原生 Python 运行环境；不以 WSL 作为唯一正式路径 | 分架构运行环境；后台计算与图形会话解耦 |
| PostgreSQL | 受支持的原生包/已有实例 | 原生服务/已有实例 | 原生服务/已有实例 |
| 本地模型 | 已有GB10特定SGLang、mixed NVFP4算子及file-backed PLE真实运行；当前128K/MTP/并发1，未测性能不作承诺 | 依据 GPU、驱动和引擎逐部署验证；不能承诺同一 NVFP4 路径 | 依据本机后端与权重格式逐部署验证；不能承诺运行 GB10 专用权重 |
| 浏览器 | 发行目标需要有对应浏览器二进制与系统库 | 对应原生浏览器与用户 profile 隔离 | 对应架构浏览器，验证签名和系统权限 |
| 桌面执行 | 用户图形会话；X11/Wayland、portal/合成器按驱动逐项确认 | 登录用户会话中的 Companion；与系统服务分开 | 登录用户会话中的 Companion；屏幕录制/辅助功能权限分别确认 |
| 后台持续运行 | 依用户服务和注销策略；显式选择是否启用 linger | 取决于登录任务/服务模式，不能假定注销后仍有桌面 | LaunchAgent 随用户会话；需无人登录计算时单独选择 daemon 模式 |
| 进程树回收 | 进程组，必要时 cgroup 资源控制 | Job Object 或等价进程树控制，验证子进程归属 | 进程组及受控子进程，验证强制退出路径 |
| 当前验收状态 | Spark 已完成本地模型、核心工作台及多项文件/恢复/自动化实测；具体边界见状态清单 | 等待真实设备验证；原生命令执行尚不支持 | 等待真实设备验证；原生命令执行尚不支持 |

纯应用、文件解析和外部 API 能力应独立于本机大模型是否可运行。Windows/macOS 可以连接用户授权的 Spark 模型端点或其他兼容端点，但这种连接不代表在该机原生运行了 GB10 权重。网络断开要显示依赖不可用和恢复路径，不能偷偷切换到未经授权的外部 API。

### 4.2 后台服务不等于桌面权限

Linux 可采用 systemd 用户服务监督 API 和 Worker；若用户要求注销后继续运行，安装向导需要解释并显式设置相关生命周期策略。systemd 的 linger 会让用户管理器在启动时创建并在注销后保留，但不因此创建一个可操作的图形桌面。[systemd `loginctl` 官方定义](https://github.com/systemd/systemd/blob/main/man/loginctl.xml)

Windows 服务运行在 Session 0，不能直接操作正常用户桌面。桌面能力必须由登录用户会话中的 Companion 执行，与服务使用受 ACL 保护的本地通信或经过配对的受控连接；不能勾选过时的“交互式服务”规避会话边界。[Microsoft：交互式服务](https://learn.microsoft.com/en-us/windows/desktop/services/interactive-services)

macOS 的 LaunchDaemon 与用户图形会话隔离；需要与用户窗口交互的能力位于用户会话组件。后台计算选择 LaunchAgent 或 daemon 时，要明确注销/登录前后行为，不把 daemon 改成 root 后就宣称能截图、输入或通过系统隐私授权。[Apple：服务与用户会话](https://developer.apple.com/documentation/XPC?language=_11)

局域网浏览器访问 Spark 只得到工作台 Web 界面，不会自动获得访问者电脑桌面。要控制另一台电脑，必须在那台目标主机安装、配对并启用 Companion；权限绑定目标主机、登录会话和有效授权，不绑定一个模糊的“当前电脑”。桌面驱动详细协议由对应文档定义，部署验收必须验证目标标签和本地停止入口。

### 4.3 能力状态模型

安装器、运行时和 UI 共同使用至少以下状态。不能只用 `enabled: true` 同时表示安装、兼容、授权和验收。

| 状态 | 含义 | 用户可采取的动作 |
| --- | --- | --- |
| 可用 | 所需组件存在、配置有效、当前授权和基础检查通过 | 执行该能力；显示验证范围和证据时间 |
| 未安装 | 目标平台存在可用方案，但本机没有组件/权重 | 查看安装清单、选择已有组件或继续不启用 |
| 待验证 | 有声明或组件，但未完成当前平台/部署的真实验收 | 查看已知证据、受控验证步骤和风险范围 |
| 不支持 | 当前平台/版本/后端明确无法提供该能力 | 显示原因、替代路径；不循环尝试安装 |
| 已禁用 | 用户策略关闭，或工作区禁止使用 | 用户在相应作用域调整策略 |
| 权限不足 | OS/工作区/桌面/网络授权未满足 | 明确需要何种权限，由用户处理 |
| 暂时不可用 | 服务退出、设备离线、资源不足、依赖故障 | 重连、排队、释放资源或查看故障 |

探测结果包含平台、CPU 架构、组件版本、后端版本、配置修订、证据来源、检查时间与失败原因。仅查询版本或检查文件不触发推理、付费 API、桌面操作或大量下载。需要调用模型才能验证的能力使用独立的显式验证操作，并展示可能的资源或费用。平台检测不能替代用户策略，更不能以“系统支持”为由默认开启敏感工具。

## 5. Spark 模型部署与资源预算

### 5.1 模型服务必须独立管理

模型服务拥有独立运行环境、启动 manifest、日志和状态，不与应用后端共用会被日常升级改写的 Python 环境。应用锁文件和模型引擎锁文件分别管理，以免安装 OCR 依赖时升级 PyTorch、CUDA 扩展或推理引擎。模型文件通过只读路径挂载/引用；转换、编译和 PLE 数据使用独立可写目录。

每个部署 manifest 至少记录以下信息：

- 模型路径、固定 revision、配置/tokenizer 与权重的来源一致性，既有校验报告引用。
- 引擎名称、确切发布版本或提交、补丁来源、Python/PyTorch/CUDA ABI、FlashInfer 与相关算子版本。
- 机器架构、GPU/驱动基线、所需系统库与安装方式；禁止仅记录 `latest`。
- 量化格式和实际支持路径、PLE/offload 策略、上下文/批次/KV 配置、推理并发和资源预留。
- 绑定地址、端口、访问凭据引用、就绪条件、退出策略与日志路径。
- 已验证能力与未验证能力，例如文本、工具、结构化输出、图像、视频、前缀缓存；分别保留输入限制。

manifest 是可审计的部署配方，不是“配置文件存在就可以运行”的证明。若引擎拒绝某个配置，必须保留失败证据并调整配方，不能把参数名映射成不经确认的同义参数。

### 5.2 GB10 与 128 GB UMA 的约束

当前权重体积接近整机统一内存规模。不能用磁盘文件大小直接推断运行内存，也不能把 CPU pinned offload 当成新增一份独立主机内存：在该 UMA 机器上，CPU 与 GPU 竞争同一总内存预算。还必须为 OS、PostgreSQL、API/Worker、KV cache、图像/音频处理、算子工作区、页缓存和模型加载过程保留空间。

已知目标路径需要 file-backed PLE，通过 NVMe 支撑相关权重/专家数据访问。其效果取决于适配实现、文件系统、NVMe 延迟与带宽、缓存热度及任务形态；不能写成“开 offload 就一定能运行”。生成 backing 文件可能需要额外磁盘空间和构建时间，安装向导应在执行前展示真实估算与目录。

本模型对应的 NVIDIA mixed NVFP4 适配必须锁定实际兼容的 SGLang 实现与 FlashInfer CUTLASS 路径，不能随意使用通用上游最新版本。当前已验证组合及资源参数位于[模型运行手册](../../runtime/model/README.md)和项目专属部署记录。新监管代码的隔离进程机制、加载中停止/资源闭合、新PLE启动和真实文本已有证据；后续一键完整启停及重启后普通关闭也已实际完成，跨boot旧记录按归属核对后归档，见[状态第20节](../implementation-status.md#20-2026-10-20-重启后正常停机修复)。完整预编译、不同条件的加载性能和压力矩阵仍未穷举，不能靠删除状态文件绕过。

最初基线不启用MTP；当前已按用户要求开启MTP，并完成128K长输入及后续真实产品流程，具体样本和测量见[模型运行手册](../../runtime/model/README.md)。历史非MTP基准不自动成为新部署的正确性、峰值内存或吞吐结论。切换引擎、量化适配、内存布局或多模态处理链路时，相关基线需要重新验证；不因名称中都含 NVFP4 而复用不匹配的性能结论。

### 5.3 资源准入与队列

资源调度分开维护模型推理槽、CPU/解析槽、GPU 辅助槽、浏览器会话、桌面独占锁、磁盘临时空间与数据库连接预算。它们不是一个全局 semaphore，也不由子 Agent 数量推导。

初始模型槽为 1。较大的 OCR、ASR、视频转换和批量文件解析默认保守串行或排队，完成实测后再提高上限。即便任务来自同一个根 Agent，也必须申请预算。子 Agent 等待资源时展示“等待模型/文件处理资源”，不能显示为正在生成 token，也不能占据模型槽等待用户回答。

准入评估采用“已测峰值 + 当前占用 + 安全余量”，没有已测数据时标记估计来源并保守处理，不伪造精确峰值。调度记录预留与释放原因，防止失败或取消后泄漏许可。资源不足时给出排队、降低输入规模、卸载可选组件、切换兼容模型的选项；不静默截断文档或压低图片质量。

优先序首先保证用户取消和停止请求能被处理，其次保护 API/数据库可响应，再分配前台交互与后台工作。已进入不可中断的安全收尾不强行打断为“已取消”，但需要显示当前阶段和结果不确定性。用户等待审批、澄清或外部设备时释放推理槽；恢复时重新准入，不保留僵尸 GPU 任务。

### 5.4 观测而非性能承诺

| 指标 | 用途 | 未知时的处理 |
| --- | --- | --- |
| 模型加载时间与峰值内存 | 判断加载方案是否有足够余量 | 显示未测，不按文件大小换算 |
| 首 token、生成速率与端到端时延 | 分离排队、prefill、decode、工具耗时 | 样本不足/不可得保持 unknown |
| CPU/GPU/UMA/可用内存 | 保护交互与数据库，解释资源排队 | 标明采样来源和覆盖范围，不累加重复统计 |
| PLE/NVMe 读写、页缓存与热度 | 解释同一请求冷热差异 | 缺少引擎计数时只展示可得 OS 观测 |
| KV/前缀缓存命中、可观测覆盖率 | 判断缓存是否有效以及数据是否完整 | 不把缺失当 0，也不把估计当真实命中 |
| OCR/ASR/浏览器工作集与任务数 | 决定可选能力并发 | 分组件测量，避免把它们都归到 LLM |
| 数据库、artifact、日志、临时目录增长 | 预警磁盘耗尽与备份空间不足 | 报告真实目录和文件系统，不报虚构容量 |

必须记录配置修订、输入规模和冷热状态，才允许比较模型性能。没有通过验证的上下文长度、吞吐、峰值内存或最大文件大小，不作为产品承诺，也不填入假样例数字。前端可以展示测量方法与“尚无数据”，不能以演示曲线填补。

### 5.5 磁盘与内存保护

磁盘按模型资产、PLE backing、artifact、staging、数据库、日志、浏览器 profile 和备份分别计量；如果它们位于同一分区，需要合并空间预算。下载/解压/转换/备份前计算额外空间，失败时清理本次拥有的临时文件，保留原始输入与已提交成果。低水位以可配置策略和实际剩余空间为准，不在尚未测量时宣称某个固定余量足够。

低水位状态下拒绝新的高空间作业、暂停非必要下载和可重建缓存写入，仍允许查看历史、取消任务、导出故障信息及执行安全清理。不能为了继续生成删掉旧记忆、活动 checkpoint、用户原文件或唯一产物。数据库磁盘不足属于需要显式呈现的严重降级，不应吞掉写入错误后继续向用户显示成功。

模型 OOM 后记录真实失败阶段、已提交的工具副作用和当前任务状态。可根据既定策略降低并发或建议用户减少上下文，但不得无限重启模型、自动改用外部付费端点，或重新执行此前已成功的文件写入/桌面动作。

## 6. 网络、安全会话和作用域

### 6.1 本机模式

默认只绑定 `127.0.0.1`；如果支持 IPv6 回环，应显式限定 `::1`，不能误绑定 `::`。数据库、模型管理端点和可选协调服务也默认不对 LAN 开放。远程浏览器通过应用后端调用模型，不直接获得本地模型服务的管理权限或外部 provider API key。

回环模式仍校验 Host 与 Origin，防止网页从其他来源利用本机入口。会话凭据不能出现在 URL、模型提示词、静态资源或事件 payload。若首次引导使用一次性凭据，应限定本机、单次有效并立即换成正常会话，日志中脱敏。修改状态的请求使用明确 CSRF 防护；SSE/WebSocket 接口同样验证身份、来源与任务作用域。

### 6.2 LAN 模式

LAN 模式由用户显式开启，开启前必须满足以下条件：

1. 已设置登录身份和本地管理者凭据；即便只有一个用户也不允许匿名读取全部工作区。
2. 指定监听网卡/地址和允许访问来源，说明防火墙影响；不能顺手打开数据库、推理引擎和桌面驱动端口。
3. 使用 HTTPS 保护远端凭据、会话和文件传输，选择受信任证书或明确的本地信任流程。证书未准备好时保留回环模式，不能默默退化为远端明文登录。
4. Cookie 设置合适的 `HttpOnly`、`Secure`、`SameSite` 与过期策略；Origin、Host、CORS、CSRF 规则一致，禁止通配可信源配合凭据。
5. 支持注销、会话撤销、凭据修改后的会话处理；事件重连重新鉴权，旧下载链接和 WebSocket 不能绕过撤销。
6. 界面明确展示当前访问方式、目标主机与工作区。LAN 使用者确认桌面动作时必须知道控制的是哪台机器。

只有一个人的首版也保存稳定 user/principal ID、workspace ID 与授权上下文，便于未来扩展，不能到多人阶段再给所有历史数据补一个含糊 owner。首版不引入组织成员层级、团队账单或企业身份平台。

### 6.3 密钥、文件与隔离

秘密优先存放在 OS Keyring，应用配置仅存引用。无可用 keyring 的环境使用经用户设置的加密 vault：主密钥由独立解锁口令或受保护的外部机制提供，不能与密文一起以明文写入同一目录。未解锁时远程连接保持不可用；无人值守启动需要单独配置解锁来源，不静默降级为明文配置。加密与密钥派生复用成熟库，不自行发明算法。文件权限使用 OS 原生权限/ACL，不能声称 POSIX `0600` 已在 Windows 等价生效。秘密不得默认进入备份、日志、诊断包、浏览器 localStorage 或模型上下文。导入 provider 配置与重新填写秘密分开。

artifact 下载必须检验当前主体、工作区和 artifact scope；临时下载凭据限制对象、期限和用途。不能允许 API 接受任意绝对路径并直接返回文件。文件授权根和允许写位置由后端校验；UI 隐藏按钮不构成权限边界。模型工具、解析器和桌面驱动都不能因为由本地 Worker 启动就继承无限文件访问。

本版原生工具进程的资源限制与超时不等于完整安全沙箱。执行不可信代码或生成脚本默认选择明确隔离提供者；不能提供所选隔离的平台标为未安装/不支持/待验证，并拒绝按原模式执行。若用户明确选择风险更高的 native_scoped 模式，须重新检查其权限和适用范围，不能静默回退或继续宣称系统隔离。可选 Docker 沙箱只传递当前任务所需文件与资源，不挂载整个 HOME、Docker socket 或数据库密钥；启用容器也不改变工具授权和审计要求。

### 6.4 账号与会话实现

首版采用本地所有者账号和服务端可撤销会话，不为浏览器自研一套长期不可撤销 JWT 系统。密码使用成熟库提供的 Argon2id 哈希与随机盐，参数保存在哈希记录并可随登录升级；可复用 `pwdlib[argon2]`。库的选择依据是维护成本和标准算法支持，工作台的 Cookie 会话是自己的设计，并不照搬教程中的 JWT 与示例用户数据库。[FastAPI 密码哈希文档](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/)。

登录成功生成高熵随机会话凭据；浏览器仅放 HttpOnly Cookie，数据库保存其摘要、主体、创建/到期时间、最近活动和吊销状态。登录和权限变化轮换凭据；绝对有效期与空闲期限分开配置。密码修改可撤销其他会话，注销立即使 SSE 重连、文件下载和回调授权失效。现有长连接也需收到吊销通知或在有界检查间隔内关闭，不能只在最初建立时检查。

登录错误采用不泄露账号存在性的文案，按来源与账号设置有界限速。状态修改检查 CSRF 与 Origin，回环与 HTTPS Cookie 配置分开测试。恢复所有者访问只能走本机受控恢复流程或已有认证会话，完成后撤销旧会话并记录审计；恢复登录不等于自动解开丢失主密钥的 vault。

## 7. 数据一致性、备份与恢复

### 7.1 数据分类和恢复范围

| 数据 | 事实性 | 备份要求 | 恢复注意事项 |
| --- | --- | --- | --- |
| PostgreSQL 会话/任务/事件/审批/checkpoint 元数据 | 权威 | 纳入一致备份 | 包括版本、对象关联、任务租约等恢复所需元数据 |
| LangGraph 持久 checkpoint | 权威运行状态 | 与对应业务状态共同备份 | 恢复必须检查运行时与 schema 兼容性 |
| Markdown 记忆与记忆修订 | 权威内容 | 纳入一致备份 | 同时保留版本和忘记/删除状态，避免恢复后复活被遗忘内容 |
| artifact 原件/导出与来源 manifest | 权威产物 | 按引用完整备份 | 数据库能解析到同批文件，不能只留文件名 |
| 用户工作区原文件 | 用户权威 | 明确是否纳入本备份 | 默认不可宣称已备份所有外部授权目录 |
| 搜索/全文索引、预览、派生缓存 | 可重建 | 可排除，记录重建版本 | 恢复后展示重建状态，不展示为缺失原件 |
| 模型权重 | 大型可复用资产 | 默认记录 revision/路径和校验引用，用户可选完整备份 | 若离线恢复需要权重，必须备份资产而非只留网址 |
| PLE backing/编译缓存 | 是否可重建取决于方案 | manifest 记录分类和重建条件 | 删除前确认不是唯一转换产物且未被服务占用 |
| provider/数据库密码等秘密 | 机密 | 默认排除，或独立加密导出 | 新机器重新授权；不能把 keyring 引用当密钥已经迁移 |
| Valkey/临时通知/租约缓存 | 非唯一事实 | 不作为必要备份 | 数据库重建协调状态 |

### 7.2 为什么单独复制目录不够

数据库、Markdown 和 artifact 不共享事务边界。数据库导出即使内部一致，也可能引用尚未复制的文件；文件复制过程中，记忆可能被更新、产物可能新增或删除。原子 rename 只避免半文件可见，不能防止两个 Worker 从同一旧版本出发产生覆盖，也不能让数据库提交和文件替换自动变成一个事务。

工作台因此需要文件修订、乐观并发检查或受作用域锁保护的写入协议，以及 artifact 发布日志/outbox 等可对账机制。正常流程先把文件写入本次 staging、完成写入确认，再在数据库提交可发布引用；中间崩溃留下待对账记录或孤立暂存，不把不完整文件标记为最终结果。Markdown 的外部人工编辑通过 revision/内容变更检测识别冲突，不能静默覆盖。

### 7.3 初版一致备份：短暂静止窗口

对单人首版采用易于理解、可验证的静止窗口，不先引入复杂分布式快照协议。界面显示即将暂停哪些写入，允许用户选择等待当前安全收尾或取消备份。

1. 创建 backup ID，记录应用/数据库/schema/运行时/组件版本、时间与备份策略，取得备份协调锁。
2. 进入写入静止状态：阻止新任务、记忆写入、artifact 发布、审批状态修改和清理；只读浏览可继续。等待正在提交的写入到达明确停点。正在执行外部不可回滚动作的任务不得被假定已经静止。停止请求优先于备份：需要处理取消或本机紧急停止时，立即使本轮备份边界失效、中止尚未完成的备份、解除静止，再按正常事务保存停止命令；不让用户等待整个文件复制，也不把改变中的备份标为一致完成。
3. 核实应用内的数据库—文件对账已经收敛，记录引用集合与每个记忆版本。用户外部编辑的授权目录必须说明快照边界；对不能冻结的外部目录，只能声明其为独立文件备份，不能保证跨系统一致。
4. 执行 PostgreSQL 逻辑导出或已验收的数据库备份方法。逻辑导出使用受支持的客户端版本，保存所需角色/权限映射与扩展清单；不把正在运行的数据库 data 目录当普通文件直接打包。
5. 在同一静止窗口复制所引用的 Markdown、artifact、相关配置和变更日志；记录包括/排除目录、文件版本/长度及必要完整性证据。只针对本备份要求校验，不为已校验且未变更的模型重复全量哈希。
6. 写出 manifest 与完成标记，检查数据库备份可读和文件引用闭合。失败备份保持不完整状态，不替换上一份有效备份。
7. 解除写入静止，恢复调度，展示真实耗时、范围、失败项、恢复入口与是否包含模型/秘密/外部工作区。

PostgreSQL `pg_dump` 可以生成数据库内部一致的导出，但只覆盖一个数据库，不自动保护外部文件或全部集群全局对象。上述静止窗口负责本应用的跨存储边界，不是对 `pg_dump` 的替代。[PostgreSQL：pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)

文件系统快照只有在覆盖数据库所需数据/WAL及所有相关路径、并满足数据库一致性要求时才能作为相应方案。不同磁盘上的“先后复制”不是一致快照。对要求更低停机时间或更短恢复点的数据量，可在后续引入经过验收的物理备份/WAL/PITR；必须同时设计 artifact/记忆版本保留，单独恢复数据库到过去时刻无法保证外部文件仍存在。[PostgreSQL：文件系统备份](https://www.postgresql.org/docs/current/backup-file.html)

### 7.4 备份 manifest

manifest 至少包含：备份格式版本、backup ID、创建来源、静止边界、应用/schema/LangGraph checkpoint 格式版本、数据库主版本和备份客户端版本、包含的工作区、逻辑对象范围、artifact/记忆修订清单、外部路径映射、模型 revision 与是否包含权重、秘密处理方式、排除项、可重建项、完整性证据与完成状态。

manifest 不保存明文密码。加密备份必须说明密钥保管与遗失后果，不能用与备份同目录的明文口令冒充保护。默认备份保留策略由用户选择并显示实际占用；只有新备份完成且旧备份不在用户保留范围时才执行清理。应用数据与备份落在同一物理设备时，必须明确这不能覆盖设备损坏风险，但不据此擅自上传云端。

### 7.5 恢复流程和恢复演练

恢复默认写入新目录和新数据库，不覆盖当前可工作的实例。步骤如下：

1. 选择可信备份，显示时间、来源、版本、工作区、包含范围和缺失项；校验 manifest 及相应数据完整性。
2. 检查目标平台、数据库版本、应用/schema 与运行时兼容矩阵。不兼容时先选择受支持版本/迁移路径，不尝试强行加载 checkpoint。
3. 恢复数据库到隔离实例或隔离数据库，恢复 Markdown 和 artifact，按 manifest 重建路径映射；缺少的原文件或模型保持明确缺失状态。
4. 重新建立本机密钥引用、用户登录与外部连接；对桌面 Companion、外部 API、网络文件和系统权限重新确认，不能自动信任备份中的会话和配对。
5. 核对数据库引用、记忆修订、删除/忘记标记和 artifact 可读性；重建索引与缓存。
6. 所有恢复的运行进入恢复评估，不自动补发付费调用、文件写入、发消息、桌面点击或其他不可逆操作。原进程租约失效，不代表外部副作用未发生；需要工具结果对账或用户决定。
7. 通过真实 UI 登录、打开目标工作区、查看历史/产物/记忆、执行一条已授权的安全任务后，才可标记“恢复验证通过”；最后由用户选择切换到恢复实例。

备份成功仅证明完成备份作业，不能代替恢复演练。最少在备份格式首次实现、schema/checkpoint 格式重要变更或修复恢复缺陷后，使用真实授权数据进行隔离恢复验收。恢复点和恢复耗时从演练记录产生，不预先承诺未测 RPO/RTO。

## 8. 升级、迁移和回退

### 8.1 版本与兼容性

至少分别记录应用版本、API/事件协议版本、数据库 schema、checkpoint 格式、工具协议、UI renderer 协议、组件包与模型部署修订。把所有变化压成一个应用版本号会掩盖不可恢复边界。

发行清单给出从哪些版本可直接升级、是否需要停机/静止、所需临时空间、是否修改数据、回退条件和迁移耗时证据。升级前检查已有任务、磁盘余量与可用备份；不能只替换可执行文件后希望旧 checkpoint 恰好兼容。

### 8.2 受控升级步骤

1. 下载到独立新版本目录，按发布 manifest 检查来源、包完整性、平台与架构、许可证和锁文件；不覆盖当前运行环境。
2. 展示变更和风险范围，准备一致备份及回退版本。已存在备份不能在未确认数据时间和格式时一概视为升级前备份。
3. 停止接单并进入安全维护窗口。API、Worker、定时清理和记忆索引写入都受同一升级锁约束；其他进程发现 schema 不兼容时只读诊断或退出。
4. 执行预先验证的 schema/数据迁移。优先扩展兼容变更，分离数据回填与破坏性删除；事务支持范围由具体迁移决定，不假定所有数据库/文件操作都能事务回滚。
5. 切换应用版本指针，启动新 API/Worker，以已有真实数据检查历史、待处理问题、记忆和产物关联；模型部署不因应用升级自动跟随更换。
6. 完成验证后解除维护并保留旧发行包及升级备份，按保留策略清理。失败则保留迁移日志和故障状态，不进入反复自动升级循环。

### 8.3 回退边界

| 失败位置 | 合理处理 | 禁止的假设 |
| --- | --- | --- |
| 下载/解包/预检查 | 删除本次临时包，继续运行旧版 | 必须先停止旧版才能下载 |
| 尚未提交的可事务迁移 | 回滚该事务，保留证据，运行兼容旧版 | 所有迁移天然可回滚 |
| 已提交但向后兼容的扩展迁移 | 按已验证矩阵回到旧应用版本 | 旧版一定忽略所有新增状态 |
| 已完成不可逆数据转换/删除 | 停止写入，恢复升级前一致备份到隔离位置，明确可能损失的新增数据 | 仅切回旧二进制就完成回退 |
| 运行时/checkpoint 格式不兼容 | 留在诊断模式，选择匹配运行时或受控迁移 | 直接把处理中任务重新从头执行 |
| 模型引擎升级不兼容 | 独立回退模型部署，保留应用和数据 | 应用数据库也必须恢复到旧时间点 |

回退不能撤销已经发生的外部副作用。升级窗口中的工具执行、外部 API、文件更改或桌面操作必须有稳定操作 ID 和结果对账，不能用数据库恢复把现实世界“回滚”。跨平台迁移优先逻辑备份和文件/权限重建，不复制另一种 OS 的 PostgreSQL data 目录、Python 虚拟环境或模型算子缓存。

## 9. 依赖选择、版本锁与许可证

### 9.1 引入规则

先复用项目选定组件、标准库、OS 原生能力与已有依赖。仅在确实存在缺口时新增组件；记录解决的问题、替代方案不能满足的原因、维护状态、平台/ABI 兼容性、运行和安装成本、许可证、数据/网络行为及退出替代路径。检查限于实际引入组件及直接影响，不扩大成无关生态审计。

开发依赖、运行依赖、可选工具、模型权重和浏览器二进制分组锁定。发行包包含锁文件和对应清单，不在运行时执行浮动升级。Python/npm 使用默认源；源码提交、外部二进制和权重使用明确官方来源和固定修订。若 ARM64 缺少 wheel，编译工具链、构建时间、临时空间和产物 ABI 要纳入组件安装清单，不能悄悄在用户日常启动时编译。

以下是选型边界，不是声称已将所有组件纳入发行包。真正发布时以锁定版本中的许可证和打包结果为准。

| 组件或能力 | 决策 | 引入前必须核实 |

### 9.3 SBOM 与供应链清单

每个发行版产生与实际产物相匹配的组件清单/SBOM：名称、精确版本或提交、来源、平台/架构、直接/间接关系、许可证表达、打包位置及必要完整性信息。模型权重、外部工具、浏览器和生成 UI 隔离运行环境也列入，不只扫描 npm 包。

SBOM 是发行追溯材料，不是全生态安全审计，也不是把所有可选候选都提前打包的理由。升级某组件时，针对受影响的兼容性、授权边界和已知问题检查；没有新变化时复用已有结论。与发布包配套保存第三方 notices 与需提供的源代码/构建材料。

## 10. 日志、诊断与故障操作

### 10.1 观测结构

每个任务事件与日志关联 `workspace_id`、`run_id`、`attempt_id`、`operation_id`、组件与配置修订；用户可以从界面复制诊断标识，但默认不把完整文件内容、模型消息和秘密写入技术日志。模型 token 统计、缓存指标与计费信息需要标记来源；未知保持 unknown。

日志按组件轮转并可在 UI 查看最近错误。持久业务事件与调试日志分开：清日志不能丢审批、待恢复动作或已完成工具结果；日志没写成功也不能把业务事实伪装为已持久化。错误报告包括发生阶段、已完成部分、是否存在外部副作用、允许的下一步和证据，而不是只显示栈追踪。

用户可导出诊断包，导出前展示包含项目和脱敏说明。默认不包含 API key、Cookie、数据库密码、完整对话、用户文件、截图或模型权重；需要包含真实内容定位问题时由用户选择相应范围，不自动上传第三方服务。

### 10.2 故障处理表

| 症状 | 应用必须保留/展示 | 安全处理 | 恢复验收 |
| --- | --- | --- | --- |
| 启动器打不开 API | 安装版本、端口、退出原因、日志路径 | 检查本应用进程和端口；允许改端口；不结束未知进程 | 重新打开后会话仍在，无重复 Worker |
| 数据库不可用 | 只读缓存的可信范围、未提交操作状态 | 停止新执行，有限重连；不创建临时内存数据库继续工作 | 恢复后通过事件/任务表对账 |
| API 重启或网络断开 | run ID、最后事件序号、待回答问题 | 重新鉴权后从游标补事件；POST 重试使用同一幂等键 | 历史完整，无重复任务和工具执行 |
| Worker 退出/机器重启 | checkpoint、租约、工具调用与结果状态 | 租约过期后取得恢复所有权，先对账再继续 | 已成功副作用不重复，结果不明项明确阻断 |
| 模型加载失败/OOM | 引擎修订、失败阶段、资源证据 | 保留其他应用能力，释放本次资源；等待用户选择或既定策略 | 成功恢复后同一任务不会丢已完成工具结果 |
| 可选 OCR/媒体组件缺失 | 缺哪个组件、原件和已提取内容 | 显示未安装/待验证及允许的替代路径 | 安装或切换后接续正确阶段，不假称已看过图片 |
| 磁盘不足 | 失败目录、真实剩余空间、已完成产物 | 停止新大写入；清理可重建且未引用内容 | 恢复后产物可读，数据库引用闭合 |
| Markdown 受管并发/已检测外部编辑冲突 | 基础修订、当前可读修订、候选更改 | 拒绝过期写入，保留差异并提供冲突处理；严格保留原件时只生成独立候选 | 检测到的冲突不被覆盖；明确外部编辑器不受应用内锁约束 |
| 桌面连接断开/截图失效 | 目标主机/会话、最后观测和动作结果 | 停止输入，重新观测与对账；必要时重新授权 | 不以旧坐标续点，本地停止仍有效 |
| 迁移或恢复失败 | 当前格式、完成步骤、未解决引用 | 留在维护/隔离状态，不覆盖最后可用数据 | 使用兼容版本或成功恢复后再开放写入 |

## 11. 验收原则和证据

### 11.1 三类状态必须分开

最终验收由主 agent 亲自执行和判断。辅助 agent 可以提供实现材料、定位问题和检查证据，但不能代替主 agent 完成关键真实操作或据其报告直接宣布整体验收。缺少某个平台、设备或权限时，主 agent 交付已完成范围和最短验证步骤，并把该项保持为“等待真实环境验证”，不把责任转交描述成已经验收。

- **实现已完成**：代码或发行包包含目标行为，并能指出实现版本；不能由文档完成推出。
- **辅助检查已通过**：静态检查、单元/协议/集成检查或命令行检查通过，记录覆盖和局限。
- **真实环境已验收**：在目标设备与实际产品 UI 中，按用户方式走完对应流程，有明确输入、操作、结果与故障证据。

当前已进入真实产品实现和验收，已完成流程见[统一状态清单](../implementation-status.md)。文档同步只复核描述、链接和事实边界，不为修改文字重新运行已有效的产品测试。未取得设备、外部凭据或维护窗口的项目继续保留，不能仅通过改文档关闭。

验收数据使用用户授权的真实文件、真实账户/目标环境和已知结果，记录适用范围；不使用模拟指标、假处理结果或伪造截图证明能力。验证外部付费接口、桌面敏感操作或文件修改前，遵守对应真实授权。测试目的应是解决本需求的具体疑点，不为凑覆盖率新增与需求无关的门禁。

### 11.2 辅助检查层次

| 层次 | 解决的问题 | 典型范围 | 不能替代 |
| --- | --- | --- | --- |
| 配置/协议检查 | 格式、版本、事件顺序、权限字段和作用域是否一致 | manifest、模型能力、工具输入输出、UI schema | 真实模型理解与桌面操作 |
| 有针对性的逻辑检查 | 幂等、租约、状态转移、取消、资源释放是否正确 | 直接影响的纯逻辑和状态机边界 | 重启后的跨进程持久化 |
| 集成检查 | 数据库、文件发布、checkpoint 与进程边界是否衔接 | 真 PostgreSQL、授权临时工作区、受控依赖 | 用户是否能从 UI 完成闭环 |
| 故障恢复检查 | 中断、重复提交、过期租约、写入冲突、结果不明如何处理 | 仅受控任务和本应用进程 | 日常可用性与可理解性 |
| 真实 UI 操作验收 | 用户流程、提示、授权、结果、恢复是否可用 | 浏览器界面到真实后端/模型/文件/桌面 | 其他平台和未覆盖模型部署 |
| 资源与性能测量 | 当前输入规模和配置能承载多少 | 已记录部署、输入规模、冷热状态 | 对未测硬件/并发的承诺 |

已有必要检查通过后，不因假设性风险反复全量回归；修复一个问题，验证修复点和直接受影响行为。平台变更、模型/引擎变更、持久格式变更有明确影响时才扩大相关检查。

U19/U20 的桌面验证不能由模拟截图或简单“API 返回成功”替代；U09 的多模态不能由模型配置字段替代；U16 的恢复不能由备份文件存在替代。验收矩阵可以按已实现阶段执行，但尚未执行项必须保留状态，不能从清单中删除来获得“全部通过”。

### 11.4 资源基线的采集方式

先记录干净空闲状态，再分别测应用空载、模型冷加载、同一真实输入的冷/热请求、上下文增长、工具调用、多模态输入、OCR/ASR 与模型争用、取消回收、服务重启恢复。测量不得擅自关闭用户进程或清空系统缓存；无法控制的背景负载作为限制记录。

每次仅为解决当前疑点改变相关参数。没有新配置或失败证据，不重复全模型校验或全硬件检查。结果应给出输入规模、样本数、分位/范围或原始测量引用、失败情况和局限，不用单次最优数字作为日常承诺。可接受阈值由产品需求与真实测量确定，不能为了文档完整填入假目标。

安全边界、幂等、持久状态和取消从首次相关功能实现时就进入，不能全部拖到 S5。S5 主要完成跨平台发布和可靠性闭环，不替前面阶段兜底补建架构。LAN 的身份与工作区作用域也应先进入数据模型，正式对外监听须在其验收通过后启用。

每阶段出口提供：实际实现版本、真实 UI 流程、必要辅助检查、失败/未验证列表、资源测量状态、下一阶段所需输入。只完成文档或代码时如实交付，不以阶段编号制造已完成错觉。

## 13. 当前操作入口

日常启动使用`./start.sh`，停止使用`./stop.sh`或`./start.sh stop`；Windows对应`start.ps1`/`stop.ps1`，但尚未真实平台验收。`status`、`doctor`、`configure-database`、`recover-account`等入口见[项目首页](../../README.md)和[一键启停说明](../../runtime/distribution/one-click-services.md)，以当前`--help`为准。

整栈关闭按工作台及受管执行、模型、搜索、数据库顺序完成，只处理当前配置可核验归属的受管组件；外部服务仍由原管理器维护。应用停止末尾需连接已有数据库核对自动化与持久命令资源，必要时仅短暂恢复同一受管集群后再关闭。`--app-only`用于单独管理应用；正常启动只恢复已登记的私有PG，不自动安装或初始化缺文件的集群。

备份、隔离恢复、清理与诊断导出通过工作台设置页操作。源码发行工具提供 `build`、`validate`、`stage`，只构建/校验/暂存，不激活新版本或执行业务迁移。当前没有 `workbench components/backup/restore/upgrade` 这一组 CLI，不应将早期命令设想复制到终端。

当前schema039的产品内备份会因媒体凭据列未纳入秘密排除审核而返回`backup_secret_schema_unsupported`，与列内是否有值无关。早期schema的真实备份/恢复及后续私有运维PG归档均保留为各自阶段证据，不据此声称当前媒体schema的可移植产品备份已就绪；详见[维护模块边界](../../apps/server/src/workbench/modules/maintenance/README.md)。
